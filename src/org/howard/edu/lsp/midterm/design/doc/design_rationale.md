# Question 2: Evolving Requirements and Design Rationale

The design already defines `RegistrationRepository` and `ConfirmationSender` as contracts, so the deployment-specific choices do not have to change the registration workflow. The application composition/configuration code can provide either a `FileRegistrationRepository` or a `DatabaseRegistrationRepository`, and either an `EmailConfirmationSender` or a `TextConfirmationSender`, to `RegistrationService`. I would add or update those implementation CRC cards when the concrete options are introduced; the service card remains focused on coordinating registration and calling the abstractions.

The important ownership decision is that `RegistrationService` coordinates the workflow, but it does not own file/database mechanics or email/text delivery details. Those responsibilities belong to repository and sender implementations behind their respective contracts. This keeps the service independent of infrastructure choices, gives each implementation a single reason to change, and allows tests to supply alternate collaborators without changing the domain classes. The tuition policy remains with `TuitionCalculator`, not with either storage or messaging class.
